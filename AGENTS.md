- **The same trap applies to pixel proxies**: a luma>230 ("white text") threshold reported zero burned captions on videos that had 274,719 amber pixels. Measure the actual design colour, or diff two renders. See D37d.
- **A modal-background picker is not a contrast measurement, and it fails silently in the *safe* direction (10-02, login/signup audit).** The collector read the modal background per element and computed `text` vs that one modal sample. For `text-white/40` the modal was the light-violet aurora panel, **not** the `BRAND.canvas` the text actually sits on — so 6 of its 20 "failures" were text that is genuinely fine, and it fired a fix on the wrong surface. Compounding it: the headings are gradient-filled (`-webkit-text-fill-color: transparent` + `background-clip: text`), so for those `color` resolves to the *fallback* colour and is meaningless while `text-fill-color` is transparent — a check that trusts `color` cannot see a gradient heading at all. Rules that came out of it: (a) contrast must be text-against-the-backing-colour-behind-the-glyphs, not text-against-a-modal-average; (b) if `text-fill-color` is `transparent`, skip the element and measure a known solid backing colour instead of trusting `color`; (c) sample glyph pixels, never a modal box. Same family as the luma>230 caption proxy: a proxy valid on one surface silently inverts on another.
- **And to "the test passes"**: the legacy-teal test asserts against *stored config only*, so it stayed green while three runtime files still hardcoded the hex. A test that reads config cannot see a hardcoded constant in source. Grep the source, then measure the pixels.
- **A mid-run snapshot is not a terminal state.** `pending_review` / `manual_review` is what the gate *records while it holds*, not what it *leaves behind*. I read it mid-run and reported a lost video; by 21:13 the scheduler had published it 4/4. Before calling anything lost, check whether a later stage, a retry, or the scheduler will consume the state. This was the costliest of the four because it nearly "fixed" a gate that was working.
- **A check that reports success it did not verify is the same failure as one that misses a real fault.** Two landed in a single session on 09-28. (a) The hand-rolled image/host parity loop reported all 8 files as MISMATCH because macOS `shasum` defaults to SHA-1 while Linux `sha256sum` is SHA-256 — it compared different digests and never could have matched. (b) A negative test run against `DEFAULT_STYLE_GUIDE` with a regex that matched nothing "passed" while proving nothing. Both failed the same way: the output was plausible and the reasoning behind it was never checked. **So: when a check fires OR passes, confirm the mechanism actually ran before believing it.** The negative test is worth nothing unless you first assert the *setup* took effect — I twice ran a "negative test" whose `git rm` had failed on a wrong path, and the green result was meaningless.
- **A counting query with a wrong regex is not evidence of absence.** `grep -oE 'Running job "[a-z_]+"'` matched nothing because APScheduler emits `Running job "name (trigger: ...)"` — no closing quote after the name — and I reported the 15:05 run as "no fire" when it had fired on time. Same for grepping `Publish complete` when the log says `PUBLISH: scheduled to 4/4`. Before declaring anything missing, print one raw sample of the expected line and copy the pattern from it.
